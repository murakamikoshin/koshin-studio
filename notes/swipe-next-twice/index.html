アプリとサーバーの点数がずれた：原因は計算ではなく、「次へ」が 2 回呼ばれてステージが入れ替わっていたこと

書いた人：Koshin（Web エンジニア・アプリエンジニア）　公開：2026-11-09

弾幕メーカー 開発の記録 ／ 2026年11月

弾幕ゲーム「弾幕メーカー」に、いま「スワイプ弾幕」というモードを作っています。短いステージ（クリップ）が次々に流れてきて、指でなぞって避け続け、点数を競うモードです。点数はランキングに載るので、アプリが送った操作の記録を、サーバーが同じ計算で遊び直して、点数を数え直しています。

このとき、アプリとサーバーの計算が合わない提出が出ました。まず疑ったのは、計算の食い違い（浮動小数の誤差など）でした。実際の原因は、計算ではなく、結果画面の「次へ」が 2 回呼ばれて、遊んだクリップがサーバーの選ぶものと入れ替わっていたことでした。この記事は、ずれた提出をサーバーに残し、「最初にずれた場所」を出すようにして原因を絞った手順と、直し方の記録です。

この記事は、弾幕メーカーのリポジトリのコミット（07a7ecd・8e68064・f19e1cc、2026 年 11 月 9 日）と、そのコードから書いています。スワイプ弾幕は開発中のモードで、名前や仕様は変わるかもしれません。

目次

  1. サーバーは、遊びをまるごと計算し直している
  2. 手順 1：ずれた提出を、そのまま保存する
  3. 手順 2：アプリにも途中経過を送らせ、最初にずれた所を出す
  4. 原因：タップと自動の「次へ」が、両方とも効いていた
  5. 直し方：画面と状態の、両方で 1 回に絞る
  6. サーバーで検算するゲームを作る人へ：確かめる 5 つ

サーバーは、遊びをまるごと計算し直している

スワイプ弾幕の 1 回のプレイは、こう流れます。

  1. プレイを始めると、サーバーが種（乱数の元）を決めてアプリに渡す
  2. アプリは、種・何本目か・連続クリア数・もう出たクリップ、から次のクリップを選ぶ（SwipeFeed.pick）
  3. クリップごとに「GO」の 60 ステップ（0.5 秒）と、プレイの最大 1,200 ステップ（10 秒）を遊ぶ。計算は 1 秒に 120 ステップの固定間隔
  4. 終わったら、クリップごとの操作の列（指の動き）だけをサーバーに送る
  5. サーバーは、同じ種から同じ順でクリップを選び直し、送られた操作で 1 本ずつ遊び直して、点数を出す

アプリ（Swift）とサーバー（TypeScript）は、同じ計算を別の言語で持っています。両者が一致することは、Swift の計算から作った正解データを TypeScript のテストで比べて確かめています。計算そのものは一致するはずなのに、実際の提出では、サーバーが途中のクリップで「被弾して終わった」と判断し、アプリが送ったクリップの数より少なく終わる（clipsPlayed < clips.length）ことがありました。

このずれは、ログに「ずれた」としか出ないと、手元で再現できません。そこで、まずずれた提出をそのまま残すことから始めました。

手順 1：ずれた提出を、そのまま保存する

サーバーの数え直しがアプリの申告と合わなかったときだけ、送られてきた操作の列と、サーバー側の途中結果を、Firestore の swipeMismatches に 1 件 1 文書で保存するようにしました（07a7ecd）。

if (result.invalid || result.clipsPlayed < clips.length) {
  logger.warn("swipe-submit-mismatch", summary);
  try {
    // Firestore の 1 文書は約 1MB まで。収まる分だけ残す
    const kept = [];
    let size = 0;
    for (const c of clips) {
      size += c.go.length + c.moves.length + 40;
      if (size > 800_000) break;
      kept.push(c);
    }
    await db().doc(`swipeMismatches/${runId}`).set({
      seed, poolVersion, sent: clips.length, kept: kept.length,
      clipIDs: result.clipIDs, clipOutcomes: result.clipOutcomes,
      scoreAfterEachClip: result.scoreAfterEachClip, clips: kept, ...
    });
  } catch (e) { logger.error("swipe-mismatch-save-failed", ...); }  // 保存に失敗しても提出は続ける
}

気をつけたのは、次の 3 つです。

  • 種とクリップの一覧の版（poolVersion）も残す。操作の列だけあっても、どのクリップを遊んだかが決まらないと再現できません
  • 1 文書の上限（約 1MB）を超えないよう、800,000 文字で打ち切る。上限を超えると書き込み自体が失敗し、何も残りません
  • 調べるための保存が失敗しても、プレイの提出は止めない。セキュリティルールでは、このコレクションをアプリから読み書きできないようにしました（allow read, write: if false）

手順 2：アプリにも途中経過を送らせ、最初にずれた所を出す

保存した記録を遊び直せば、サーバー側の計算は追えます。でも、アプリの中で何が起きていたかは分かりません。そこで、アプリがクリップごとに途中経過を数えて、操作の列と一緒に送るようにしました（8e68064）。サーバーは同じものを自分でも数え、上から順に比べて、最初に食い違った 1 か所を返します。

比べる順名前中身
1g0クリップを始めた時点のゲージ（前のクリップまでの結果）
2grazesかすり（弾の近くを通った）の回数
3bombsボムが出たステップの一覧
4endクリップが終わったステップ
5cp120 ステップ（1 秒）ごとの、弾の位置の指紋
6scoreクリップを終えた時点の点数
 
function firstDiff(clips, result) {
  for (let i = 0; i < Math.min(clips.length, result.diag.length); i++) {
    const c = clips[i].diag, s = result.diag[i];
    if (!c) return { clip: i, field: "no-diag" };
    const same = (a, b) => JSON.stringify(a) === JSON.stringify(b);
    const checks = [["g0", c.g0, s.g0], ["grazes", c.grazes, s.grazes], ["bombs", c.bombs, s.bombs],
      ["end", c.end, s.end], ["cp", c.cp.slice(0, s.cp.length), s.cp], ["score", c.score, result.scoreAfterEachClip[i]]];
    for (const [field, app, server] of checks) if (!same(app, server)) return { clip: i, field, app, server };
  }
  return null;
}

作るときに決めたことを、書いておきます。

  • 弾の位置は、そのままではなく丸めてから指紋にする。弾の x・y を 1,000 倍して整数に丸め、FNV-1a でまとめた値です（bulletHashCoarse）。小数の最後の桁まで比べる指紋も別にありますが、調べる目的では、丸めた方が「本当に別の動きをしたか」だけを拾えます
  • 毎ステップではなく、1 秒ごと。1 クリップ最大 10 個で済み、送る量が増えません
  • 途中経過は、点数に使わない。アプリの申告なので、信用すれば書き換えられます。形が合わなければ（整数でない、配列が長すぎる等）黙って捨て、比べるだけに使います
  • 原因に近いものから比べる。ゲージがずれていれば、それより後の数字はみな巻き添えでずれます。最初の 1 か所だけを返すのは、そのためです

あわせて、保存された記録を Swift 側の同じ計算で遊び直す調査用のテスト（SwipeMismatchReplayTests）も足しました。環境変数で記録のファイルを渡したときだけ動き、アプリの選び方で出るクリップの順と、サーバーが記録したクリップの順を並べて出します。浮動小数の誤差を疑って、かすりや被弾の判定が「境目ぎりぎり」だった弾の数も数えるようにしています。

原因：タップと自動の「次へ」が、両方とも効いていた

保存と途中経過を入れてから約 40 分後のコミット（f19e1cc）で、原因を直しました。計算の食い違いではなく、アプリが遊んだクリップと、サーバーが選んだクリップが、別物になっていたのです。

クリップをクリアすると結果が出て、約 1〜1.6 秒で自動的に次のクリップへ進みます。その前にタップ（または上スワイプ）すれば、すぐ次へ進めます。直す前のコードは、こうでした。

// SwipeScene（画面）
private func advance() { resultTimer = 0; onAdvance?() }   // タップでも、タイマーでも、ここを通る

override func update(_ currentTime: TimeInterval) {
  ...
  if model.phase == .cleared || model.phase == .failed {
    if !touching { resultTimer -= dt }
    if resultTimer <= 0 { advance(); resultTimer = 99 }
  }
}

// SwipeModel（遊びの状態）
func advanceAfterResult() async {
  switch phase {
  case .cleared, .go, .playing: await nextClip()   // GO やプレイ中でも、次のクリップを選んでいた
  case .failed: await finish()
  default: break
  }
}

コードから読める流れは、こうです。

  1. 結果画面でタップすると、advance() がタイマーを 0 にしてから、次へ進む処理（onAdvance）を呼ぶ。この処理は Task で後から走る
  2. その処理が走る前の次のフレームでは、状態はまだ「クリア画面」のまま。タイマーは 0 以下なので、自動の「次へ」がもう一度呼ばれる
  3. 1 回目の呼び出しでクリップ A が選ばれ、先読みが済んでいれば、すぐ「GO」に進む
  4. 2 回目の呼び出しは「GO」中に届く。advanceAfterResult は GO 中でも nextClip() を呼ぶので、もう一度クリップを選ぶ
  5. まだクリップ A の記録は付けていないので、「何本目か」は同じ。でも「もう出たクリップ」には A が入っているので、別のクリップ B が選ばれる

プレイヤーは B を遊び、B の操作の列を送ります。サーバーは同じ種・同じ「何本目か」から A を選び、B のための指の動きで A を遊び直すので、まったく別の弾幕の中で被弾します。アプリでは避けきった記録が、サーバーではそのクリップで終わる、という形になります。

2 回呼ばれても、タイミングによっては害がありません。2 回目が「切り替え中」（.transition）に届けば、何もしないで終わります。先読みが済んでいて、1 回目がすぐ「GO」まで進んだときだけ、入れ替わりが起きます。毎回は起きないので、見つけにくい不具合でした。

直し方：画面と状態の、両方で 1 回に絞る

直したのは 2 か所、合わせて 6 行の追加と 3 行の削除です。

// 画面：一度進んだら、次の結果画面でタイマーが入れ直されるまで、何度呼ばれても無視する
private func advance() { guard resultTimer < 90 else { return }; resultTimer = 99; onAdvance?() }
...
if resultTimer <= 0 { advance() }

// 状態：次のクリップを選ぶのは、開始直後か、クリア画面のときだけ
private func nextClip() async {
  guard phase == .starting || phase == .cleared else { return }
  ...
}
func advanceAfterResult() async {
  switch phase {
  case .cleared: await nextClip()   // GO・プレイ中に呼ばれても、選び直さない
  case .failed: await finish()
  default: break
  }
}

画面の側だけ直しても、ほかの入口（別のボタンや、将来足す操作）から 2 回呼ばれれば同じことが起きます。「クリップを選ぶ」という、記録と結びついた処理の側で、呼ばれてよい状態を限ったのが本命の直しです。画面の側の直しは、余計な呼び出しを入口で減らすためのものです。

この記事を書いた時点では、直した版での提出で、ずれが無くなったかを数えた結果はまだありません。swipeMismatches は残してあるので、次に数えるときの材料になります。

サーバーで検算するゲームを作る人へ：確かめる 5 つ

この件から、同じ形の作り（アプリが操作を送り、サーバーが遊び直す）で使えることを、手順にしておきます。

  1. ずれた提出だけ、元の入力ごと残す。種・データの版・操作の列があれば、手元で何度でも再現できます。保存先の大きさの上限と、保存の失敗で本処理を止めないことに注意
  2. アプリにも途中経過を数えさせ、サーバーが「最初にずれた 1 か所」を返す。点数には使わず、比べるだけ。原因に近い順に並べる
  3. 「何を遊んだか」を決める処理は、呼ばれてよい状態を限る。乱数で何かを選ぶ処理が 2 回走ると、計算が完璧でも結果がずれます
  4. タップと自動タイマーのように、同じ処理への入口が 2 つあるなら、片方を通ったら、もう片方を閉じる。「タイマーを 0 にして進む」は、自動の側の条件を満たしてしまうことがあります
  5. Task で後から走る処理は、その間にも画面のループが回る。状態が変わるのは処理が走ってからなので、それまでのフレームは古い状態のまま判断されます

サーバーの検算が合わなくなった別の例は、すし積むの番付に載らなくなった記録に書いています（こちらは、ゲームの数字を変えて検算の数字を直し忘れた件です）。弾幕そのものの作り方は、弾幕の作り方にまとめています。

ほかの記録

  • 弾幕の作り方：放射・自機狙い・雨・渦巻き・追尾の仕組みを、計算式と動く見本で解説 — 弾幕は短い計算式でできている。弾幕メーカーで実際に使っている放射・自機狙い（奇数弾と偶数弾）・雨・首ふり扇・渦巻き・追尾の式を、動く見本で確かめられるように書いた。
  • すし積むの番付に載らなくなった：ゲームの数字を変えて、サーバーの検算を直し忘れていた（しかも二つ） — 番付に、普通に遊んでも載らなくなった。ゲームの数字を変えて、サーバーの検算を直し忘れていた。金の桶の褒美（8,000→25,000）と、降るネタ（3種→5種）の二つ。注意書きでは守れず、同じ種で出題を比べる検査を足した。
  • ポケカ・トレカ抽選アプリを比較：トレカダッシュ・トレゲト・NowPokeca・Pokeka Tracker・トレカの地図のメリットとデメリット — ポケカをはじめトレカの抽選・予約・再販を追うアプリ・サイトを、ジャンル数・通知・地図・料金で比較。作者（トレカダッシュの開発者）による比較で、トレカダッシュの弱いところも書いた。
